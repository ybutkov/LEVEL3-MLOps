# Cyclic encoding (циклическое кодирование)

> Конспект для week-3. Как кодировать «часовые» признаки — hour_of_day, month, day_of_week — чтобы модель видела их природу.

## 1. Проблема — ordinal плох для цикла

У нас в `final_dataset` есть `hour_of_day` со значениями 0..23, `month` 1..12, `day_of_week` 0..6. Сейчас они хранятся как обычные целые числа (ordinal integers).

Что неправильно с этим для **линейных моделей** (linear regression / Ridge / Lasso) и моделей, считающих расстояния (k-NN, SVM, нейросети)?

### Пример: hour_of_day

- 23:00 (полночь -1ч) и 00:00 (полночь) — это **1 час разницы** в реальности.
- В ordinal-кодировке `|23 - 0| = 23` — модель видит «разница 23», как будто 23:00 и 00:00 — это две противоположности дня.
- Линейная модель строит коэффициент `β_hour`, который умножает значение часа. Если `β > 0`, она думает: «чем выше час, тем больше аренд». Но реальный паттерн не монотонный — пик в 8 утра и 17 вечера, минимум ночью.

### Похожая проблема с `month`

- Декабрь (12) и январь (1) — соседние месяцы (зима).
- В ordinal `|12 - 1| = 11`. Модель видит их как «максимально далёкие».

### Когда это **не** проблема — tree-based modeли

Деревья (Decision Trees / Random Forest / XGBoost) делают разбиения вида `hour > X`. Они могут построить структуру:
```
если hour < 6: low demand
если 6 ≤ hour < 9: rising
если 9 ≤ hour < 16: medium
если 16 ≤ hour < 19: high
если hour ≥ 19: declining
```

То есть для деревьев ordinal-представление **работает** — просто им нужно больше split-ов. Они не страдают от расстояния «23 - 0 = 23», потому что не считают расстояния.

**Но:** для `month`, где «декабрь близок к январю» нельзя выразить через одну упорядоченную ось, дерево всё равно делает несколько разбиений и тратит «глубину» на это. Cyclic encoding снимает нагрузку.

## 2. Sin/Cos transformation

Идея: представить циклическую величину как **точку на единичной окружности**. Тогда «расстояние» (Euclidean distance) между точками соответствует реальной цикличности.

### Формулы

Пусть `x` — значение признака, `T` — длина периода (для часа `T=24`, для месяца `T=12`, для дня недели `T=7`):

```
x_sin = sin(2π · x / T)
x_cos = cos(2π · x / T)
```

Это два новых числовых признака вместо одного.

### Почему два, а не один

Если оставить только `sin`, то у функции `sin(2π·x/24)` есть **точки с одинаковым значением**: например, `sin(2π·3/24) = sin(2π·9/24) = 0.707` — то есть 3:00 и 9:00 попадут в одну точку. Информация потеряна.

С двумя осями `(sin, cos)` — каждое значение `x` получает **уникальную позицию** на окружности. Это и есть «развернуть линию 0..23 в круг».

### Проверка идеи на руках

```python
import numpy as np

hours = np.arange(24)
sin_h = np.sin(2 * np.pi * hours / 24)
cos_h = np.cos(2 * np.pi * hours / 24)

# 23:00 → точка (sin≈-0.26, cos≈0.97)
# 00:00 → точка (sin=0.00, cos=1.00)
# Евклидово расстояние ≈ 0.26 — близкие.

# 12:00 → точка (sin=0.00, cos=-1.00)
# 00:00 → точка (sin=0.00, cos=1.00)
# Евклидово расстояние = 2.00 — максимально далёкие. Верно: 12 часов разницы.
```

## 3. Что становится с линейной моделью

Линейная модель с ordinal `hour`:
```
ŷ = β₀ + β₁ · hour
```
Может выучить только **монотонный** тренд по часу. Реальный паттерн (двугорбый) не выучивается.

С cyclic-encoded `hour`:
```
ŷ = β₀ + β₁ · sin(2π·hour/24) + β₂ · cos(2π·hour/24)
```
Это **синусоида с произвольной фазой и амплитудой** — `A · sin(2π·hour/24 + φ)`, где `A = √(β₁² + β₂²)`, `φ = atan2(β₂, β₁)`. Одногорбый паттерн (один пик) ловится отлично.

Двугорбый паттерн (пик 8 и пик 17) — не ловится одной синусоидой. Нужны **гармоники** (harmonics):

```
x_sin1 = sin(2π · hour / 24)
x_cos1 = cos(2π · hour / 24)
x_sin2 = sin(4π · hour / 24)  # вторая гармоника
x_cos2 = cos(4π · hour / 24)
```

Сумма двух синусоид может ловить двугорбые паттерны. На практике для bike-rental: попробовать 1-2 гармоники для `hour_of_day`, одну для `month`, одну для `day_of_week`.

## 4. Реализация в коде

### Вручную через pandas

```python
import numpy as np

def add_cyclic(df, col, period):
    df[f"{col}_sin"] = np.sin(2 * np.pi * df[col] / period)
    df[f"{col}_cos"] = np.cos(2 * np.pi * df[col] / period)
    return df

dataset = (
    dataset
    .pipe(add_cyclic, "hour_of_day", 24)
    .pipe(add_cyclic, "month", 12)
    .pipe(add_cyclic, "day_of_week", 7)
)
```

### Через `FunctionTransformer` в sklearn Pipeline

```python
from sklearn.preprocessing import FunctionTransformer
import numpy as np

def sin_cos(x, period):
    """x — 2D ndarray (n_samples, n_features). Возвращает (n_samples, 2*n_features)."""
    return np.column_stack([
        np.sin(2 * np.pi * x / period),
        np.cos(2 * np.pi * x / period),
    ])

hour_encoder  = FunctionTransformer(sin_cos, kw_args={"period": 24})
month_encoder = FunctionTransformer(sin_cos, kw_args={"period": 12})
dow_encoder   = FunctionTransformer(sin_cos, kw_args={"period": 7})
```

Дальше эти трансформеры идут в `ColumnTransformer` (см. [[_notes_sklearn_pipeline]]).

### Готовый трансформер (sklearn >= 1.5)

```python
from sklearn.preprocessing import SplineTransformer
# или используй sklearn-contrib пакеты
```

В новых версиях sklearn есть `SplineTransformer` (циклические splines), но это уже расширение — для baseline достаточно простого sin/cos.

## 5. Подводные камни

### (a) Cyclic + дерево = бесполезно

Если ты уже решил, что используешь только XGBoost / Random Forest, cyclic encoding **не даст выигрыша**. Дерево всё равно сделает свои split-ы по ordinal. Иногда даже ухудшает: одна фича стала двумя, поиск split-а становится тяжелее.

**Правило:** cyclic encoding — для **линейных моделей** и **нейросетей**. Для деревьев — оставляй ordinal.

В пайплайне это решается через `ColumnTransformer`: для линейной модели — sin/cos, для дерева — pass-through.

### (b) Линейность vs нелинейность внутри цикла

Cyclic encoding ловит **smooth periodic** паттерны (плавные синусоидальные). Если реальный паттерн «острый» (например, ровный спрос всю ночь, потом резкий скачок в 7:00) — синусоида плохо ловит резкий переход. Тогда нужны:
- Больше гармоник.
- Или one-hot encoding для hour_of_day (24 бинарных колонки вместо 2 sin/cos).

One-hot даёт максимум гибкости (любая модель часов), но: 24 фичи vs 2, риск переобучения, теряется циклическая близость соседних часов.

### (c) `day_of_week` для линейной модели — спорно

Цикл 7 дней — да, формально циклический. Но **поведение в субботу/воскресенье качественно отличается** от будней (см. `is_weekend`). Линейная модель с sin/cos по day_of_week может выучить smooth-паттерн, который не соответствует «ступеньке» weekend vs weekday.

Альтернатива: оставить `is_weekend` (бинарный) + one-hot для конкретных дней, или sin/cos + `is_weekend` дополнительно.

### (d) `month` — циклический, но не симметричный

Декабрь и январь близки по календарю (соседи), но в bike-rental поведение может быть разным (январь — после праздников, декабрь — перед). Sin/cos навяжет «близость», которой нет. Это аргумент в пользу one-hot или ordinal для `month` даже в линейной модели — но только если данных хватает.

## 6. Декомпозиция времени для bike-rental

Какие фичи в принципе можно вытащить из `datetime_hourly`:

| Фича | Тип | Период | Закодировать как |
|---|---|---|---|
| `hour_of_day` | циклическая | 24 | sin/cos (1-2 гармоники) для линейной; ordinal для деревьев |
| `day_of_week` | квази-циклическая | 7 | sin/cos + `is_weekend`; или one-hot |
| `month` | квази-циклическая | 12 | sin/cos для базовой сезонности; либо ordinal/one-hot |
| `year` | линейная | — | ordinal (есть рост +65% между годами) |
| `day_of_month` | без явного цикла | ~30 | обычно неинформативна, пропускаем |
| `week_of_year` | циклическая | 52 | избыточна с month |
| `is_weekend` | бинарная | — | как есть |
| `is_holiday` | бинарная | — | как есть |

Главное: не дублировать одну информацию в разных кодировках для одной модели — линейная модель закоррелированные фичи может «делить» между ними непредсказуемо. Деревья толерантнее.

## 7. Резюме

- **Линейные модели / нейросети:** sin/cos для `hour_of_day` и `month`, плюс `is_weekend` отдельно. Опционально — вторая гармоника для `hour_of_day` (двугорбый паттерн).
- **Tree-based (RF, XGBoost):** оставляем ordinal `hour_of_day`, `month`, `day_of_week`. Cyclic encoding не нужен, лишние фичи только мешают.
- **`ColumnTransformer`** — позволяет дать разные кодировки для разных моделей в одном пайплайне, не дублируя датасет.
- Проверка: после кодировки fit-ни одну линейную модель и посмотри на `R²` относительно ordinal-варианта. Если разница большая (5+ pp) — cyclic кодировка реально нужна.
