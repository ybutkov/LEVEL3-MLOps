## 1. Структура финального датасета

**Гранулярность: почасовая. 17 379 строк.**

Якорная таблица — `weather`. Она уже почасовая, и именно к ней всё присоединяется. Rental-события агрегируются до часа и джойнятся левым джойном.

Это работает без потерь: rental-часы и weather-часы совпадают на 100% — 0 rental-часов вне weather, 0 weather-часов с арендами вне таблицы аренды.

### Итоговые колонки (~12 до feature engineering)

| Колонка | Источник | Тип | Примечание |
|---|---|---|---|
| `datetime` | weather (spine) | datetime | почасовой timestamp |
| `temperature_c` | weather | float64 | |
| `perceived_temperature_c` | weather | float64 | |
| `humidity` | weather | float64 | |
| `windspeed_kmh` | weather | float64 | |
| `conditions` | weather | ordinal int (1–4) | 4 класса: clear/clouds/light_rain/heavy_rain |
| `is_holiday` | holidays | int (0/1) | match по дате |
| `registered_count` | registered_rentals | int | агрегат за час |
| `direct_count` | direct_rentals | int | агрегат за час |
| `total_rentals` | вычисляемая | int | **таргет** = registered + direct |

### Решения по типам

**`conditions` → ordinal int, не one-hot:**
Порядок тяжести есть (clear < clouds < light_rain < heavy_rain), поэтому ordinal логичен. One-hot — решение модели, а не данных. Хранить строку в проде нецелесообразно: дорого, нет гарантии консистентности. Энкодер ставится в sklearn Pipeline перед моделью.

**`is_holiday` → бинарный int (0/1):**
Это уже финальное представление — не энкодинг категории, а просто факт. Никакой альтернативной трактовки нет.

**Два счётчика отдельно (`registered_count` + `direct_count`), не только `total_rentals`:**
Registered и direct — разные поведенческие сегменты (разница в объёме 4.3x). Их соотношение может само по себе быть признаком. Таргет — `total_rentals`, но оба компонента остаются в датасете.

## 2. Пропущенные часы в weather

В диапазоне 2011–2012 ожидается 17 544 часа, в датасете 17 379 — **165 пропущенных часов**. Ни в одном из них нет аренд. Скорее всего — плановый перерыв сервиса (ранние ночные часы). Они корректно выпадают из финального датасета.

## 3. Анализ праздников

### 3.1 Разброс по праздникам

Средний обычный день: **4 527 аренд**.

| Праздник | Аренды | Отклонение |
|---|---|---|
| Christmas Day | 1 013 | −3 514 |
| Dr. Martin Luther King Jr.'s Birthday | 1 000 | −3 527 |
| Washington's Birthday | 1 107 | −3 420 |
| Thanksgiving Day | 1 495–2 425 | −2 100–−3 032 |
| Memorial Day | 4 098–6 043 | −429–+1 516 |
| Labor Day | 3 351–6 034 | −1 176–+1 507 |
| Independence Day | 6 043–7 403 | +1 516–+2 876 |
| Columbus Day | 5 117–5 478 | +590–+951 |

Диапазон: от 1 000 до 7 403 — разброс в **7x**.

### 3.2 Гипотеза: температура объясняет разброс

**Метод:** линейный тренд по обычным дням (температура → аренды), затем остатки для праздников.

**Результат — гипотеза опровергнута.** Стд остатков обычных дней = 1 512. 12 из 21 праздничных точек выходят за пределы ±1 стд даже после контроля на температуру.

| Праздник | Ср. температура | Аренды | Остаток |
|---|---|---|---|
| Labor Day 2011 | 23.7°C | 3 351 | **−2 340** |
| Christmas Day | 5.7°C | 1 013 | **−2 168** |
| Washington's Birthday 2011 | 6.3°C | 1 107 | **−2 153** |
| Memorial Day 2011 | 26.5°C | 4 098 | **−1 985** |
| Independence Day 2012 | 29.1°C | 7 403 | **+953** |
| Columbus Day 2012 | 10.0°C | 5 478 | **+1 692** |
| Veterans Day (observed) | 14.8°C | 6 269 | **+1 816** |

Паттерн после контроля:
- **Стабильно ниже нормы:** Thanksgiving, Christmas, Washington's Birthday — семейные праздники, люди уезжают из города.
- **Около нормы или выше:** Independence Day, Columbus Day, Veterans Day — активные/уличные праздники.

### 3.3 Можно ли разбить праздники на больше групп?

**Нет. Данных недостаточно.**

Ключевая проблема — вариация внутри одного праздника между 2011 и 2012 сопоставима с вариацией обычных дней:

| Праздник | Остаток 2011 | Остаток 2012 | Разница |
|---|---|---|---|
| Labor Day | −2 340 | +120 | **2 460** |
| Washington's Birthday | −2 153 | +21 | **2 174** |
| Memorial Day | −1 985 | +98 | **2 083** |
| Thanksgiving | −2 225 | −1 077 | 1 148 |

Стд внутри группы сопоставим со стд обычных дней (1 512). Любая схема с 3+ группами будет заучивать шум.

### 3.4 Настоящая причина: рост сервиса между 2011 и 2012

2012 стабильно на **+65%** выше 2011 во всех 12 месяцах без исключений:

| Месяц | 2011 | 2012 | Рост |
|---|---|---|---|
| Январь | 1 240 | 3 189 | +157% |
| Апрель | 3 164 | 5 788 | +83% |
| Июль | 4 510 | 6 540 | +45% |
| Сентябрь | 4 278 | 7 329 | +71% |
| Декабрь | 2 867 | 4 090 | +43% |

Именно это объясняет разброс: Labor Day 2011 выглядит провалом не потому, что это "плохой тип праздника", а потому что весь 2011 был в 1.65x меньше 2012.

## 4. Итоговые решения по feature engineering для `is_holiday`

| Вариант | Проблема |
|---|---|
| Бинарный `is_holiday` только | Не различает летние и зимние праздники |
| `holiday_type` (winter/summer/civic) | 1–2 наблюдения на группу, заучивание шума |
| `holiday_name` с target encoding | Можно, но только с правильным fold'ом (лик иначе) |
| **`is_holiday` + `year` + `month`** | **Рекомендуется** |

Модель сама научится взаимодействию `is_holiday × year × month` — `year` улавливает рост сервиса, `month` косвенно разделяет зимние и летние праздники.
