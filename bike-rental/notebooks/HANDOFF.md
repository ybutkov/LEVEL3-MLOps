- **Основная задача (почасовой тотал):** `eda_and_modeling.ipynb`. `final_dataset` агрегирован до

- **Per-location — заморожен как копия:** `modeling_per_location.ipynb` (баннер «Parked» сверху).
  Полная прежняя работа (baseline → #1 Ridge → #2 conditions → #3 RF на ~365K строк) сохранена там

## Где мы сейчас
EDA закончена. Модель — в `eda_and_modeling.ipynb` (почасовой тотал):
- Датасет: 17,379 строк, таргет mean≈190 / median 142 / max 977, **нулей нет**, skew 1.28.
- **Baseline = `LinearRegression`.** На validation: MAE 138.97, RMSE 174.70, R² 0.388
  (mean-baseline MAE 194, R²<0).
- **Улучшения** (лог: «меняем одну вещь, мерим на validation»):
  - #1 Ridge — **no-op** (n≫p), отличия в 4-м знаке. Negative result.
  - #2 `conditions` one-hot vs ординал — **+0.002 R²**, шум; оставлен ординал.
  - #3 **`RandomForestRegressor`** — MAE 49.4, RMSE 79.7, **R² 0.873** (без тюнинга). Бьёт по слабости
    baseline: недооценке дневных пиков и переоценке ночного провала (8:00 факт ~509 / LR ~252 / RF ~504;
    3:00 факт ~17 / LR ~159 / RF ~18). Importances: доминирует `hour_of_day` (~0.60), затем
    `days_since_launch` и температура.
  - #4 **`HistGradientBoostingRegressor`** (sklearn, бустинг) — на validation **R² 0.892** (MAE 50.6,
    RMSE 73.5), чуть лучше RF; RMSE/MAE 1.45 (ошибка однороднее). Дефолт; больше итераций — хуже. **Выбранная модель.**
  - #5 **ablation `perceived_temperature_c`** — corr 0.99 с `temperature_c`, но удаление роняет HGB
    R² 0.892 → 0.879 (линейной нейтрально) → **оставляем**. Урок: избыточность решает ablation, не корреляция.
- **TS-CV** (5 фолдов train+val): HGB 0.78 ≳ RF 0.76 ≫ LR 0.26 — выбор HGB подтверждён, переворот на test = шум.
- **Финал на test** (один раз): LR R² 0.410 · RF 0.859 · **HGB 0.841**. Ранжирование RF/HGB на test
  перевернулось vs validation (val=лето, test=зима) — в пределах ~0.02 R², иллюстрация слабости одного фолда.
- **Следующее:** **Dagster-интеграция** (главный недоделанный deliverable). Моделирование исчерпано.

## Ключевые решения (зафиксированы)
- **Гранулярность:** почасовой тотал (см. выше). Per-location — отдельный parked-ноутбук.
- **Сплит:** хронологический **70/15/15** по уникальным таймстампам, строго по времени.
  train 2011-01…2012-05-27 · val …2012-09-12 · test …2012-12-31.
  **Test трогаем ОДИН раз в самом конце**, после выбора модели; всё сравнение/ablation — на validation.
- **Таргет:** `total_rentals` (почасовая сумма), raw (не log1p — log1p резко проигрывает, R²<0).
- **Лик:** `registered_rentals`/`direct_pickups` в признаки НЕ идут (их сумма = таргет; в агрегате их и нет).
- **Тренд:** фича `days_since_launch` (не `year`).
- **Один базовый `final_dataset`** (строки+таргет+сплит заморожены); представление фич — в sklearn
  `Pipeline`/`ColumnTransformer` (cyclic sin/cos для линейной; деревьям — raw integers).
- **EDA-находки (city-wide, дневной агрегат — `exploration_*`):** рост сервиса +65% год-к-году,
  двухрежимный (фаза запуска ≈ янв–апр 2011 + органический режим с мая 2011). Праздники: бинарный
  `is_holiday` не различает зимние/летние; богатую кодировку решает ablation, не глаз (21 праздник — мало данных).

## Решено: бустинг через sklearn (не XGBoost)
XGBoost на macOS — двойной блокер: `xgboost-cpu` без macOS-wheel (нужен cmake для сборки из исходников),
а у полного `xgboost` wheel есть, но он требует системный OpenMP (`libomp.dylib`, обычно `brew install libomp`).
По договорённости **всё ставим через uv-окружение, без brew/системных библиотек** → XGBoost убран из
зависимостей; #4 сделан на sklearn `HistGradientBoostingRegressor` (то же семейство histogram gradient
boosting, нативно в sklearn, везёт свой `libomp`). Результат эквивалентен. `pyproject` больше не содержит xgboost.

## Слабые места и приоритеты
Методология крепкая, выводы честные. Держать в голове:

**Шатко / под вопросом:**
- **Решения на ОДНОМ фолде валидации (лето 2012).** no-op'ы (Ridge, conditions) — ок; для margin'ов
  нужен **TS-CV**, чтобы им доверять.
- **val=лето, test=осень/зима** — валидация сезонно узкая, может плохо предсказывать test.
- **Только 2 года** — сезонность и праздники оценены по 1–2 наблюдениям. Потолок данных.
- **R² 0.87 у RF выглядит высоко** — но это **легче** прежней per-location задачи (R² 0.76): агрегация
  по киоскам усреднила шум. Не путать «модель лучше» с «задача проще» — числа двух ноутбуков несравнимы.

**Дыры (диагноз есть — действия нет):**
- **Коэффициенты линейной модели не смотрели.**

**Сделано:** **TS-CV** (5-фолдовый `TimeSeriesSplit` на train+val) — усреднённо HGB R² 0.78 ≳ RF 0.76 ≫ LR 0.26;
порядок тот же, что на одиночной валидации, выбор HGB подтверждён. Разброс по фолдам (std 0.09–0.14) ≫ зазора
HGB–RF (~0.02) → переворот RF/HGB на test был шумом, не сменой лидера.

**Перекос:** handout просит time-box и оставить время на Dagster-интеграцию (её ещё нет).

**Приоритет действий:** 1) ~~#4~~ **сделан** (HistGradientBoosting); 2) ~~TS-CV~~ **сделан** (выбор HGB подтверждён);
3) **Dagster-интеграция** — главный оставшийся deliverable: ассет-агрегатор `hourly_totals` →
`trained_model` → `.joblib` IO-manager; 4) остальное (коэффициенты, лаги) — если останется время.

## Запуск на новой машине
1. Клонировать main, переключиться на ветку `bike-rental/week-3-modeling` (там зависимости week-3).
2. `uv sync` — ставит всё (sklearn, joblib, matplotlib, nbconvert, ipykernel). xgboost из зависимостей
   убран, блокеров нет — всё через uv, без brew/системных библиотек.
   На малом home-разделе venv/кэши лучше класть на большой диск (на исходной машине — `/goinfre`); адаптируй.
3. `data/raw` (107 МБ) → пайплайн материализует `data/processed/final_dataset.csv`. **Ноутбуки читают
   `final_dataset.csv`**, а не raw (`data/processed` в .gitignore → на свежем клоне его нет).
4. Материализовать пайплайн (создаёт `final_dataset.csv`):
   `uv run dagster asset materialize --select '*' -m bike_rental.definitions`.
5. Прогон ноутбука: `python -m nbconvert --to notebook --execute --inplace eda_and_modeling.ipynb`.
6. `_scratch` — опционально (черновики; все выводы уже в ноутбуках).
